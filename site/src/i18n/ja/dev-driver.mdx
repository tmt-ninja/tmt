driver は、端末の host や agent プログラムの扱い方を tmt に教えます。外部 host driver はすでに利用でき、Herdr の driver は tmt に同梱されています。[driver プロトコル](https://github.com/tmt-ninja/tmt/blob/main/contracts/driver-protocol-v1.md)が操作と通信形式を定義しています。

<Mdx.h3 id="two-kinds">2種類の driver</Mdx.h3>

<Terms>
  <dt>host driver</dt>
  <dd>
    ペインを探し、出力を取得し、入力を届け、フォーカスを切り替えます。tmux は組み込みで、Herdr
    は外部実行ファイルを使います。
  </dd>
  <dt>runtime driver</dt>
  <dd>
    agent を認識し、hook を読み、起動や再開を組み立てます。Claude Code、Codex、agy、Pi
    には組み込みの runtime driver があります。
  </dd>
</Terms>

<Callout title="外部 runtime driver はまだ動作に使われません。">
  runtime driver
  の承認と一覧表示はでき、承認時には宣言された書き込み先が表示されます。認識、起動、hook、setup
  はまだ外部 runtime driver を使いません。承認しただけでは組み込み driver を置き換えません。
</Callout>

<Mdx.h3 id="a-driver-is-a-program">driver はプログラム</Mdx.h3>

外部 driver は実行ファイルです。tmt は操作ごとに JSON リクエストを渡して1回呼び出し、1つの JSON 応答を読みます。driver の種類に応じたプロトコルの機能と操作を実装し、制限時間、サイズ上限、エラーの意味に従ってください。結果が不確かな送信を自動で再試行してはいけません。

開発には[プロトコル crate と適合テスト](https://github.com/tmt-ninja/tmt/tree/main/rust/crates/tmt-driver-protocol)を使えます。同梱の [Herdr driver](https://github.com/tmt-ninja/tmt/tree/main/drivers/herdr)は、契約と合わせて読める外部 host の実装例です。

<Mdx.h3 id="approve-and-inspect">承認して確認する</Mdx.h3>

承認は自分で端末から実行します。受け入れる前に実行ファイルが宣言する機能を確認してください。

<Cmd>{`
$ tmt driver install ./tmt-driver-screen
$ tmt driver ls
$ tmt driver rm screen
`}</Cmd>

サードパーティーの driver には明示的な承認が必要です。同梱の Herdr driver は例外で、Herdr ペインから初めて `tmt ls` など host を扱うコマンドを使うと承認されます。Herdr を削除すると、明示的に再インストールするまで自動で再承認されません。

<Mdx.h3 id="changes-and-removal">変更と削除</Mdx.h3>

承認済みの実行ファイルが見つからない、または変更された場合、tmt は以前の承認を信頼せず、その状態を報告します。同梱 driver の更新では、宣言する機能が増えていなければ承認を引き継げます。host driver を削除しても binding は保存されますが、再承認されるまで使えません。

<Mdx.h3 id="keep-state-in-its-owner">状態は担当する側で管理する</Mdx.h3>

ペインが存在するか、入力が届いたかを推測せず、プロトコルの確認情報とエラー応答を使います。tmt が binding を検証し、identity とリクエストを自身のストレージに保存します。driver はそのデータベースを開いてはいけません。agent 設定の変更は、ユーザーが同意した setup の処理に任せます。
