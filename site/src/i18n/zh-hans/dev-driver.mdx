driver 教 tmt 如何操作终端 host 或 agent 程序。外部 host driver 已可使用；Herdr 的 driver 随 tmt 提供。[driver 协议](https://github.com/tmt-ninja/tmt/blob/main/contracts/driver-protocol-v1.md)定义了操作和通信格式。

<Mdx.h3 id="two-kinds">两种 driver</Mdx.h3>

<Terms>
  <dt>host driver</dt>
  <dd>查找窗格、捕获输出、传递输入和切换焦点。tmux 已内置；Herdr 使用外部可执行文件。</dd>
  <dt>runtime driver</dt>
  <dd>
    识别 agent、读取其 hook，并规划启动或恢复。Claude Code、Codex、agy 和 Pi 都有内置 runtime
    driver。Cursor Agent 支持基本检测与调用方识别，但没有生命周期钩子或精确恢复会话功能。
  </dd>
</Terms>

<Callout title="外部 runtime driver 尚未参与运行。">
  你可以批准并列出 runtime driver；批准时会显示它声明的写入位置。识别、启动、hook 和 setup
  尚未使用外部 runtime driver。仅批准它不会替换内置 driver。
</Callout>

<Mdx.h3 id="a-driver-is-a-program">driver 是一个程序</Mdx.h3>

外部 driver 是可执行文件。tmt 为每项操作调用它一次，传入一个 JSON 请求，再读取一个 JSON 回答。请实现协议中对应 driver 类型的能力和操作，遵守时限、大小限制和错误含义。结果不确定的发送不得自动重试。

开发 driver 时可使用[协议 crate 和一致性测试工具](https://github.com/tmt-ninja/tmt/tree/main/rust/crates/tmt-driver-protocol)。随附的 [Herdr driver](https://github.com/tmt-ninja/tmt/tree/main/drivers/herdr)是外部 host 的实现，可对照契约阅读。

<Mdx.h3 id="approve-and-inspect">批准与检查</Mdx.h3>

请亲自在终端中批准。接受之前，先阅读可执行文件声明的能力：

<Cmd>{`
$ tmt driver install ./tmt-driver-screen
$ tmt driver ls
$ tmt driver rm screen
`}</Cmd>

第三方 driver 需要明确批准。随附的 Herdr driver 是例外：在 Herdr 窗格中首次运行 `tmt ls` 等操作 host 的命令时会自动批准。移除 Herdr 后，必须明确重新安装，才会再次获准使用。

<Mdx.h3 id="changes-and-removal">变更与移除</Mdx.h3>

已批准的可执行文件缺失或发生变化时，tmt 会报告问题，而不会继续信任旧批准。随附 driver 更新时，只要声明的能力没有扩大，就可沿用批准。移除 host driver 会保留其 binding，但再次批准 driver 之前无法使用。

<Mdx.h3 id="keep-state-in-its-owner">由负责的组件保存状态</Mdx.h3>

请使用协议的证据和错误响应，不要猜测窗格是否存在或输入是否已送达。tmt 负责验证 binding，并在自己的存储中保存 identity 和请求。driver 不得打开该数据库。agent 设置的变更应由用户已同意的 setup 流程处理。
